## 压力来源

- **常驻内存主要来自 AstrBot/NapCat/QQ。** 主机总内存约 1.6 GiB；统计服务部署前，可用内存已经只有约 200 MiB。AstrBot/QQ 容器未配置内存上限，重启后的容器内存峰值约 994 MiB。12:55 附近，AstrBot 进程的 PSS 与 SwapPSS 合计约 236 MiB，QQ 主进程约 160 MiB，另有多个 QQ 子进程。故障前没有逐进程内存历史，长期增长幅度待采样确认。
- **APT 自动更新是最强的触发线索。** 启动时间、缓存写入时间、约 100 MiB 的匿名内存增长和首次内存压力提示紧密衔接；该任务没有内存预算，I/O 使用普通优先级。
- **原来的交换策略加剧了文件缓存压力。** 故障期间 2 GiB swap 始终未使用，`vm.swappiness=0` 使内核推迟交换匿名页，优先挤压文件缓存。文件缓存反复读入与回收可以解释大量读取和持续等待。[Linux 内核说明](https://docs.kernel.org/admin-guide/sysctl/vm.html#swappiness)
- **统计服务的健康检查存在额外开销。** 主 Node 进程在重启后采样时，PSS 与 SwapPSS 合计约 37 MiB；每分钟另起 Node 进程执行 `fetch` 的健康检查，会短时触碰容器的 96 MiB 上限。12:52:04–12:53:19 的采样中，12:53:00 健康检查与一次 `memory.events:max` 增长对应，累计读取仅 0.12 MiB。这个检查值得减负；本次恢复后的采样没有复现持续大量读取。`max` 表示内存分配即将超过上限并触发回收，本次 `oom`、`oom_kill` 均为零。[cgroup 内核说明](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- **磁盘预读可能放大读取量。** 当前虚拟磁盘预读为 4 MiB，来自 tuned 的 `throughput-performance` 配置。其在内存紧张时的影响需要单独对照测量。

统计数据库主文件仅 16 KiB，WAL 约 73 KiB，统计访问日志约 138 KiB；故障前正常时段约每小时 120 次统计读取，成功事件上报很少。故障阶段的磁盘写入也仅约 0.01–0.03 MiB/s，压力集中在读取。图片 API 已停止两天。

## 处置建议

1. 优先减少统计服务健康检查开销，用轻量 HTTP 检查替代额外 Node `fetch` 初始化，并测量检查期间的内存峰值与读取量。
2. 为 APT 自动更新配置低 I/O 优先级和经过测量的资源预算，继续保留安全更新。
3. 保存轻量的逐进程或容器内存、I/O 历史，以定位 AstrBot/QQ 的长期增长及下一次后台任务峰值。
4. 单独评估磁盘预读量，依据对照结果决定是否从 4 MiB 下调。

上一轮恢复已将 `vm.swappiness` 调整为 30。12:53 附近可用内存约 1.13 GiB，swap 使用约 439 MiB，内存 PSI `avg10=0.00`、I/O PSI `avg10=0.05`。午间调查阶段只读取服务器状态。
